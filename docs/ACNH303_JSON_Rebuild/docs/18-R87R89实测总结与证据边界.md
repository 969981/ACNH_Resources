## 二、Ghidra 与原始 ELF 地址纠正

- 原版 ELF SHA-256：`145903c25d37a7c90e8818440bcf462b3dca490e11e45cf435605ab00d709664`。
- Ghidra 输出 `image_base = 0x00100000`，**Ghidra 地址减去 0x00100000 才是 ELF 地址**。
- R89 真正校验并合并 1.076 GB SQLite 分片，实际包含 25,000 个已导出函数、**8,332,586 条 XREF**、**2,892,486 条符号**，总函数 59,997，因此完整函数反编译尚未结束。

R88/R89 两层交叉确认的两个真实 AArch64 直接调用：

| Ghidra 调用点 | 原始 ELF BL 指令 | 原始 ELF 目标 | Ghidra 目标 |
|---|---|---|---|
| `00EE53B4` | `1D010094` | `00DE5828` | `FUN_00EE5828` |
| `00F08758` | `92000094` | `00E089A0` | `FUN_00F089A0` |

`FUN_00EE5828` 有 `Camp_InduceFailFlag` 原版字符串读取，`FUN_00F089A0` 有 `Camp_InduceFailAlreadyInduced` 原版字符串处理。两个目标各有 1 个 `UNCONDITIONAL_CALL`、1 个 `INDIRECTION` 与 1 个 `DATA` 静态引用。

> [!caution] 上游所在函数仍需 Ghidra 实际地址集合验收
> R89 在已导出的函数索引中发现最接近调用点的入口分别为 `_INIT_3366` 和 `_INIT_3403`，但这两条调用点距离各自入口 **3444/3384 字节**，超过函数索引的 `byte_count=2992`。不能据此断言它们实际位于上述 `_INIT_` 函数体内，更不能认定属于游戏实时邀请判定函数。必须用 Ghidra 的 Function Body AddressSet 判断实际归属。

## 三、仍未实现的真正最终判定

目前仍**没有**完成 `EventFlowQueryCanInduceNpc`（或 `IsCallableAmiiboNpc`）→ Native 查询注册表 → 目标函数 → 当前存档/联机上下文 → 返回 case 的闭环。完整查询名称在原始 ELF 中没有按可见字面字符串存在，不能靠 `rg` 强行找。所有 **417 位普通村民**的“正常入住”“跨岛接走”“露营地邀请”“amiibo 邀请”四个字段都应保持 UNKNOWN；没有任何一位被本轮错误标为 TRUE/FALSE。

**明确的下一个验证点**：在 Ghidra 12.2 对两处 `BL` 的 Source Address 调用 `getFunctionContaining()` 而不是近似函数入口；再检查 EventFlow 查询处理器注册表及读取 NPC 当前存档状态的真实函数，并在游戏实机中核对。
